### Clean integration validation recipe

1. Preserve the customized baseline and candidate inputs outside the publication tree. Record the source HEAD, baseline patch hash and per-file input hashes. Derive the feature delta from baseline to candidate for mixed files; do not use a whole-file HEAD-to-candidate diff for those files.
2. Prepare a separate clean integration checkout at the recorded compatible Chief source commit. Apply only the reviewed feature delta and intended new modules/assets/skills/docs. A failed patch is a conflict to inspect, not permission to copy the customized file wholesale. Retain required customized dependencies only through separately reviewed commits or an explicitly documented downstream baseline.
3. Confirm the clean integration diff contains no lifecycle/customer work, private identities, owner-specific activation scripts, runtime state, credentials, generated root logs or unrelated binaries. Validate all newly referenced modules are tracked. Inspect repository-relative source and test changes independently.
4. Run type checking, focused lint, independent trust tests, queue/service/scanner/provider/control tests and the real isolated runtime/browser fixture from that clean checkout. A compile failure proves the feature delta depends on omitted baseline work and must be resolved before claiming reproducibility.
5. Record the resulting clean commit and test evidence as the feature release. If building the owner's installer from the customized baseline plus the feature, identify that artifact separately and record the complete dirty build-input hashes and baseline patch hashes. Do not claim the feature commit alone reproduces the owner-custom binary.
6. Test the exact packaged server and native restart, then compare installed resources to the tested artifact. Push only the explicitly selected branch to the verified owner fork. Public release/upload is separate from a source push. Never include recovery/runtime material merely to make an archive appear complete.
