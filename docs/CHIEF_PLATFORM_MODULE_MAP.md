# Selected Platform source modules for Chief

Source audit, 2026-10-07. **Proposal and dependency evidence only; none of these Platform packages has been imported into Chief's application build.** Source files downloaded under `.chief-local/platform-module-audit/source-release` are private inspection material. The current Chief office remains the independent implementation documented in `CHIEF_HULY_REUSE.md`.

## Provenance and accepted scope

Preferred baseline: release tag `s0.7.426` resolves to annotated tag object `f7d60427b1f5fec844b77a3c1141c6a76fd25eaf`, which peels to commit `03b7aad7dc562f4f9769c51a4df08191a0393997`. All source links and manifest measurements below refer to [Platform-Collective/platform at `03b7aad7dc562f4f9769c51a4df08191a0393997`](https://github.com/Platform-Collective/platform/tree/03b7aad7dc562f4f9769c51a4df08191a0393997). The recursive Git tree and raw files were retrieved from GitHub, with local fetch receipts and SHA-256 inventory. This is distinct from the installed reference image **`platformcollective/front:s0.7.426`**: the source release tag matches the image tag name, but the image binary’s derivation from this commit has **not** been attested. A tag or familiar screen does not prove matching models, migrations, API contracts, or bundled modules. No live Platform records, credentials, or container configuration were read for this audit.

The owner's selected scope is actual source reuse for Office personal spaces and meeting rooms, including a whole-team room; flexible information/knowledge modeling with Cards, Spaces and Types; Contacts first; Inbox/notifications; Explore Cards; Slack-like human channels, direct messages and Threads; Tracker; editable Documents; a persistent, collapsible right companion panel switching between day calendar/Planner and compact Office; and the separate full Team planner. Existing Chief Routines and the original agent Team map stay. HR and Processes are deferred. Detailed Contacts analysis belongs to the separate Contacts audit; contact identity remains a shared dependency of every human-facing module.

The scoped source headers and root [LICENSE](https://github.com/Platform-Collective/platform/blob/03b7aad7dc562f4f9769c51a4df08191a0393997/LICENSE) identify EPL-2.0. Preserve source headers, license text, exact revision, modified-file records, and source distribution provenance when retaining code. Do not relabel copied code as Apache-2.0 or treat the existing Chief implementation as a Platform derivative merely because both use LiveKit. No restricted Chief/OpenMaus enterprise code is needed for this mapping.


The earlier develop audit used `bf00cde6765de1b66311d8c92e7e129261412877`. Git blob comparison across 211 inspected files found 188 identical and 23 changed at the release pin. Selected UI/domain model files and their resource manifests are identical in this inspected set. Differences include service/pod Docker build scripts, communication foundation package scripts and a chunter migration guard: develop checks `domainExists(DOMAIN_COMMENT)` before updating/moving old comments or deleting backlinks; the release does not. The release Docker scripts use direct shell invocations where develop adds a Node shell wrapper, so plan a compatible build environment instead of assuming the develop Windows build fixes exist in the release. This is a scoped comparison, not a claim that the entire revisions are equivalent.

## Do not conflate the two Chat generations

The old model uses `ChunterSpace`, `Channel`, `DirectMessage`, `ChatMessage extends ActivityMessage`, and `ThreadMessage` attached to the parent activity message. Its source also contains `__migratedToCard` and `__migratedUntil` fields. Those markers show a migration boundary exists; they are not proof that the installed workspace has migrated or that every old feature has exact parity in the new UI.

The newer model uses a Chat application operating on Cards/Types and the communication package family. `models/chat/src/index.ts` creates the Thread system type, and `plugins/communication/src/direct.ts` defines a Direct card. Communication Message has a `cardId` and `threads` collection, with its own message ID/creator/date representation. `server/server-pipeline/src/communication.ts` registers a communication operation domain/middleware, and `foundations/communication/packages/server/package.json` depends on the communication Cockroach adapter, account client, server token and hulylake client. This is more than a rename of `ThreadMessage`.

**Proposed choice:** keep the coherent Cards + new Chat + communication stack for the retained-source experiment if its pinned UI satisfies the owner's channels/DMs/Threads acceptance checks. Retain legacy chunter compatibility where the selected Office/Tracker packages still import it. If the installed screen is legacy chunter and exact parity is required first, retain that coherent legacy stack instead; do not mount new Chat over old message storage without a tested migration. Establish this using a disposable workspace and source-built bundle, not production contact/message reads. Both implementations are human Chat; neither should be presented as Chief's agent thread store.

## Configurable Types versus the CES game examples

Cards are a flexible information/knowledge model, not a game-specific schema. `MasterTag extends Class<Card>` and tag mixins provide type-specific properties and relationships. `ManageMasterTags.svelte` queries model tags; `settings/GeneralSection.svelte` checks the `setting.mixin.Editable` flag and exposes type settings. `models/card/src/index.ts:createSystemType` deliberately sets that flag false on system types; the inspected registrations include File and Document. `models/chat/src/index.ts` adds the system Thread type. These are positive source distinctions between configurable types and protected system types.

The owner-observed CES names **Character, Enemy, Environment, Game asset, Game Component and Game narrative** are not present in the inspected card/chat model registrations, card migration or card English labels. They are consistent with workspace/sample configuration, but their exact creation/seed origin in the installed workspace has **not been established**. Do not claim they are mandatory system types, delete them, or create a fresh workspace to make them disappear. Preserve the configurable engine; any choice to omit game-specific sample records belongs to a separate, explicit seed/import decision. No live type records were inspected for this conclusion.

## Proposed smallest coherent retained boundary

This is an **initial retained-source boundary**, not a proven minimal transitive closure or an implementation decision already completed:

1. Preserve Chief's React shell, agent runtime, private agent history, Routines and Team map. Start with the Contacts audit's narrow retained entry. Add a boundary adapter for identity, authorized navigation and selected-record handoff; keep member credentials out of private agent routes.
2. Retain a separately built Svelte Platform module host with its native model registration, resource loader, workbench/panel/view/presentation infrastructure, assets and themes. Seed only the selected app registrations in a disposable model/workspace. Reusing Svelte UI inside React directly would require a deliberate mount/lifecycle boundary; an iframe or separate origin is not itself a finished authentication or privacy design.
3. Keep the selected domain/model/UI/assets/server packages as matched families: contact, love/presence, card, chat/communication, inbox/notification, compatibility chunter, tracker/task, document/text-editor, calendar and time. Keep supporting activity, attachment/uploader, preference, account/client/core/platform and their **resolved** dependency closure. Do not copy only the leaf `.svelte` files and claim retained-source functionality.
4. Keep source-compatible account, workspace/model initialization, transactor, storage and collaboration services for the experiment. Replacing them with Chief's JSON office store is a new backend port, not a small UI integration. Runtime scope is separated below.
5. Prune visible HR and Processes applications because they are deferred; do not blindly delete their packages. `tracker-resources` imports `hr`; `communication-resources` imports `process`; `time-resources` imports `lead`, `recruit` and `board`. Remove or adapt the specific feature imports and corresponding registered resources only after static dependency/build and disposable behavior tests prove they are unused in the selected surfaces.

No full repository import, service deployment, database migration, identity federation or new module UI is authorized by the existence of this document alone. The owner's selected work authorizes preparation; parent integration coordinates the concrete implementation boundary.

## Disposable acceptance gates before calling a slice implemented

- Contacts: create/edit/search a synthetic person/company; preserve identity and permission semantics; verify no real contact import.
- Office: personal space, ordinary room and whole-team room; invitation acceptance, capacity/membership, participant-only notes, media grants and leave/reconnect behavior. Agents never gain private member data solely by occupying a shared room.
- Cards/Spaces/Types: create space/type/card, change allowed fields and permissions, rich edit/reload, move/parent/rank, collaborator subscription; preserve the separately verified Assigned/Created/Subscribed meanings.
- Human Chat: channel membership, private DM, reply thread, unread/notifications and attachment visibility with two people and an outsider. Confirm whether tests target legacy chunter or new Card Threads and include migration only if explicitly selected.
- Tracker/Documents: create/assign/change issue status; edit and reload rich documents; concurrent editing and forbidden cross-space reads. Do not substitute controlled-documents workflows or agent conversations.
- Shell companion panel: left navigation selects Cards, Contacts, Inbox and other main features independently of right-panel state. Right panel has closed, day calendar/Planner, and compact Office states; users can collapse or switch it without replacing the main page. Preserve selected state through main-module switches and reload. Verify both desktop and narrow-width behavior.
- Calendar/Team: the day calendar shows a horizontal current-time indicator that advances, and clicking an eligible time opens scheduling. Verify actual persisted event creation, time zones and permissions. Keep the separate Team planner agenda/work slots and full calendar surface. These are required acceptance behaviors; this audit has not executed their implementations.
- Shared Office state: compact and full Office consume the same people, presence, rooms and meeting membership. Remain on a Card, discuss that Card, and invite a person using compact Office without navigating away. Check real-time state consistency when another participant accepts or leaves.
- New Chief enhancement, not an asserted Platform capability: dragging a person's face/contact tile into a room prepares/sends an invitation under the chosen workflow; another person must accept before joining, while self-drag uses the normal authorized self-join flow. Provide click and keyboard equivalents. Show truthful pending/accepted/declined/expired/joined/left states; never auto-capture microphone/camera or imply invitation acceptance equals media connection.
- Boundary: retained service restart/build on synthetic data, same-revision model/UI/server compatibility, no upstream updater overwrite, visible failures for unavailable connectors. Existing Chief Routines and Team map must remain functional.
